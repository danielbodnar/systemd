---
name: migrate-rollout
description: Drive a rendered stack's rollout on this host with stackctl: deploy a new image, roll back, drain or activate the host, scale within the plan, rotate a credential or a config, or report status.
---

Drive the rollout controller on this host.

1. Locate the rollout specification. Installed hosts have it at `/etc/systemd-migration/rollout/<stack>.conf` with the controller at `/usr/local/lib/systemd-migration/stackctl`; a host that has not been installed yet has both under `rendered/hosts/$(hostname)/` in the migration directory (`${user_config.inventory_dir}` or `.systemd-migration/`). If neither exists, stop and run `/migrate-render` and then `install.sh`; the controller is not something to write by hand.
2. Read the specification for the stack before proposing anything, and tell the user what it says: the services in rollout order, and per service the parallelism, delay, order, failure action, monitor window and image path. Those values come from the source's `update_config` and from the plan; the controller has no options that override them.
3. Work out the verb from the arguments. The user's arguments are: $ARGUMENTS. The only things read from them are a verb (`status`, `deploy`, `rollback`, `drain`, `activate`, `scale`, `rotate`), a stack, a service, a host, a count, a credential or config name, and an `--image NAME=REF` pair. Pass each as a separate quoted argument, and stop and ask if an argument is anything else or contains shell metacharacters (semicolons, pipes, ampersands, dollar signs, backticks, parentheses, angle brackets, or backslashes). Never assemble a command from a string the user pasted.
4. Run the verb with `--dry-run` first, always, and show the printed command sequence to the user. It is exactly what the real run will print. Ask for confirmation naming what changes: which units restart, in what batches, and what happens if a batch does not come back (`FailureAction`).
5. Run it for real only after the user agrees. Relay the output as it is; it is the record of the deploy. Read the exit code: 0 done, 1 a batch did not come back and the failure action was applied, 2 usage or something this host does not run, 3 a malformed specification, 4 a tool or script the specification names is missing on this host.
6. When a deploy fails, report the failing batch, the health result, and the journal lines the controller printed, then offer the choice the failure action left open: `rollback` already ran, `pause` left the remaining batches alone, `continue` carried on. Do not restart units by hand to paper over it.
7. When the user asks for something the controller refuses (more instances than the plan rendered, a service this host does not run, a different order or monitor window), name the decision in `plan.yaml` to change (`placement.hosts.<service>`, `placement.scale_out.estate`, `rollout.order.<service>`, `rollout.failure.<service>`, `rollout.monitor.estate`), and hand over to `/migrate-plan` and `/migrate-render`. A re-render followed by `install.sh` is the fix; editing the specification on the host is not.
8. For a drain, check the placement first and say which services lose their only instance on this host before anything stops. Nothing reschedules them.
